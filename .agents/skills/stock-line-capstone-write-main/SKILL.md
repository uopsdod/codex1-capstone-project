# LINE 留言修改門檻：功能建置

## 成果、來源與範圍

同一官方帳號支援「門檻改成 2%」與「查詢門檻」。新增或沿用「LINE 留言修改跌幅門檻」工作流，和原股價通知共用唯一門檻。修改本身不查行情、不發股價通知；本人合法留言可由工作流用 reply API 回覆，不另發 push。

承接 $stock-line-capstone-write-prerequisite 的本次證據，缺項先補。技術建置在同一對話使用 $n8n-workflow-builder，不要求另開聊天或子代理。先讀 [實作規格](references/implementation.md) 及 [共用指令邏輯](references/command-processing.js)，採已驗證路徑，再核對本次平台能力。

直接交辦執行此 Skill 時，依序完成必要的共用門檻遷移、原通知更新、指令入口上線與一次本人手機修改測試。沿用原正式工作流、課程共用 JSON 與現有設定。使用者要求只做到草稿、只讀 Skill 或修改教材時，依指定範圍處理。需要本人登入、由工具要求確認，或要替換用途未確認的既有 Webhook 時，只交接眼前那一步，完成後接續。

## 1. 保存及遷移設定

- 保存原草稿、啟用版本、連線與非秘密設定，回復資料只留本機受限位置，不上傳課程 repo。保留憑證引用，不匯出秘密。
- 同專案建立或沿用 stock_alert_settings 的唯一 stock_drop_threshold 列。初始化沿用原通知實際門檻，不能直接使用2%等範例。遇舊表差異先以本次正式讀回及已確認用途決定，避免覆寫較新的設定。
- 門檻與事件欄位依實作規格準備；保留既有其他欄位。股票及本人路由仍取原通知設定節點，若表內有舊股票欄位，要清楚標示未作目前來源。
- 原通知每次開始讀取唯一有效門檻，計算、IF、Flex使用同次快照。移除設定節點內第二份獨立門檻；缺列、重複列或無效值停止，不回退舊值。執行中收到的新值由下一次採用。
- 股票、行情、本人路由、憑證、卡片、去重、時區與排程保留。先隔離驗證，不跑可能推播的正式手動入口。原通知已啟用時，驗證後發布遷移版並保持啟用；原先未啟用就維持未啟用。避免正式版讀到半套設定，改動後修復受影響畫布分組。

## 2. 建立安全指令草稿

- Webhook 使用 rawBody；先以受保護 Crypto 憑證計算原始位元組的 HMAC-SHA256/base64，再比對 x-line-signature。缺失／錯誤簽章回403，不讀寫設定、不回LINE。不能重新JSON序列化來驗簽；沒有安全秘密機制就停止這項延伸，不影響原通知。
- 驗簽後才解析，限定已確認本人一對一文字訊息。群組、他人與非文字不改設定，不回覆陌生使用者。有效空events／無可處理事件回200。
- 對外預設「門檻改成 2%」，保留舊格式「門檻 2%」相容，接受前後空白及省略百分號。門檻大於0、小於100、最多兩位小數；拒絕負值、科學記號及附帶內容。不用模型猜測任意聊天。格式錯誤給本人簡短範例。
- 更新前取得原值，按實作規格帶版本條件提交門檻及事件狀態，再讀回確認，才回覆成功與下次生效時間。回覆中的前後值動態產生。
- **查詢不改門檻**，可以記錄事件去重及回覆狀態；不能將技術紀錄寫入誤報成變更門檻。
- 持久處理多事件、重送及舊事件，不以一般先查後寫宣稱原子控制。競爭失敗不回覆成功；讀回 redelivery 狀態，關閉時不承諾LINE會自動重送。replyToken只用於當次回覆，結果不明不盲目重試。
- 設定提交、回覆保留、LINE接受及手機看到分開記錄。寫入成功但回覆失敗仍保留設定成功事實；沒有寫入不得回覆已更新。

## 3. 建置驗證

先做隔離指令、本人限定、空／多事件、重送、亂序、無效設定及簽章正反測試，再以隔離表測實際條件寫入。測試值、模擬本人及回覆不得進入正式資料或發給他人。不要對相同驗收反覆建立新流程；已有測試副本就沿用。

使用真正Test URL驗證原始HTTP；本次MCP輸入若缺raw binary就改用已確認的測試接收方式，不放寬驗簽。標明由瀏覽器啟動／實際HTTP送入／MCP讀取Execution各自作用。自行簽署的fixture不是LINE真正Verify；模擬事件不是本人操作。

原通知使用不推播副本確認共用門檻傳到計算、IF及Flex。沒有達標股票正常不發，不偷偷降低門檻。只檢查一般使用需要的判斷，不引入極微小數值差異作額外驗收門檻。資料庫實際故障、極端併發等未測情境明列限制，不冒稱全部通過。

## 4. 發布上線與驗證

建置驗證通過後，在同一對話接續以下步驟。先讀回工作流的發布狀態及 LINE 頻道設定，沿用已完成項目。

1. 尚未發布或啟用時，發布並啟用「LINE 留言修改跌幅門檻」，讀回啟用版本並取得正式 Webhook URL。
2. LINE 已設定相符 URL 時直接沿用。URL 空白時填入正式 URL。若已有不同 URL，先確認用途與是否可替換，再處理。
3. 確認 URL 相符後，若 Use webhook 尚未開啟則開啟。執行 LINE Verify，並確認結果顯示 Success。若已有同一正式入口的成功證據且設定仍相符，沿用該結果。
4. 保留原股價通知的股票、目前門檻、排程與啟用狀態。Verify 通過後，直接告訴本人手機要傳哪一句修改指令，接續下節驗證。

若Verify逾時，先查Execution；有效空events已成功且沒有副作用時，可再驗證一次。以LINE顯示Success與正式Execution共同確認，持續失敗就排錯，不無限重試。

## 5. 手機實測：一次一步

1. 確認上線成功後，沿用本人已選定的正式目標值，給出可直接傳送的句子，如「門檻改成 2%」。若本人未選定，提供一條與目前門檻不同的合法指令作為測試建議，說明傳送後會修改正式值，由本人決定是否傳送或改用其他值。說明新值會保留、下次股價檢查生效，不立即發股價通知。
2. 請本人到自己的官方帳號聊天室傳送，回覆「已傳送修改門檻指令」及收到的結果，等待回報。再讀取對應Execution、共用列與回覆紀錄，核對前後值。不能代傳或改表冒充手機測試。
3. 修改確認後，再請本人傳「查詢門檻」。等待回報，核對查詢紀錄及手機顯示與共用值一致，且門檻未變。API接受不等於手機收到；已有清楚截圖或本人確認就不重問。
4. 空白或無法辨識的圖片，先查工具證據，再請補眼前缺少的手機結果；不要求重傳已成功指令。不要因測試結束自動恢復舊值。
5. 修改成功後，用原通知的不推播副本讀取正式共用表，確認新門檻傳入真實行情計算、跌幅判斷及有達標股票時的 Flex 卡片。核對正式通知使用相同的設定來源與判斷邏輯；首次自動執行依實際紀錄另行驗證。只有本人另外要求送測試通知才發授權次數：沿用Flex版型及當前股票門檻，沒有達標時明標「設定測試」及實際行情日期，不冒稱達標卡片，不改門檻或正式去重。
